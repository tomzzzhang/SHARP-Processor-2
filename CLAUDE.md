## Project Overview

SHARP Processor 2 — a modern desktop app for qPCR/isothermal amplification data analysis. This is a ground-up rewrite of the v1 PyQt6+matplotlib app using **Tauri 2 + React + TypeScript + Plotly.js**.

## Tech Stack

- **Frontend:** React 19, TypeScript, Vite 8, Tailwind CSS v4, shadcn/ui, Plotly.js (via react-plotly.js + plotly.js-dist-min)
- **State:** Zustand
- **Backend:** Tauri 2.x (Rust)
- **Python sidecar:** For instrument file parsing (.pcrd, .tlpd, .eds, .amxd) via scoped shell command
- **Build:** Tauri CLI → `.exe` x64+x86 (Windows), `.app` (macOS)

## Build & Run

### Windows
```bash
# Double-click dev.bat, or:
set CARGO_TARGET_DIR=%cd%\build-cache
npx tauri dev
```
- **CARGO_TARGET_DIR** is set to `build-cache/` inside the project directory (handled automatically by `dev.bat` and `build.bat`).
- Requires: Rust (stable), VS 2022 Build Tools (C++ workload), Node 24+
- Rust targets: `x86_64-pc-windows-msvc` (64-bit), `i686-pc-windows-msvc` (32-bit)
- `build.bat` builds both x64 and x86 installers → `dist-release/windows-x64/` and `dist-release/windows-x86/`

### macOS
```bash
# Prerequisites: xcode-select --install, Rust via rustup, Node 24+
chmod +x dev.sh build.sh
./dev.sh          # development
./build.sh        # production DMG → dist-release/macos/
```
- First launch: right-click > Open to bypass "unidentified developer" warning (ad-hoc signed)
- Xcode Command Line Tools required (not full Xcode)

## Parser Principles

### Time reconstruction: always use the most stringent source available (MANDATORY)

**If real timestamps exist in the file, use them. Never fall back to an average / assumed cycle duration when per-read times are recorded.** An averaged axis is silently wrong — it looks plausible and quietly rescales every kinetic readout.

Priority chain for the amplification time axis:
1. **Per-read timestamps** recorded by the instrument (always prefer these).
2. Instrument telemetry with real time resolution (e.g. TianLong `TempData`).
3. Protocol-derived step durations (sum of holds/ramps).
4. **Last resort:** spread the run duration, or a hardcoded per-cycle constant — and only when nothing above exists.

Additional rules:
- **Zero on the first amplification read**, not on run start. A run's wall-clock start includes the initial hold (and the file's end time includes the melt ramp), so rebasing on run start — or spreading run-duration across cycles — inflates the axis.
- **Use only the amplification stage's reads.** Melt-ramp reads are a different stage; including them (or the whole run span) stretches the axis.
- Timestamps can be encoded more than one way in the same format family — probe for all of them before giving up and averaging.

Where each parser gets its time (all now use real timestamps, averages only as true fallback):

| Format | Real time source | Fallback |
|--------|------------------|----------|
| `.pcrd` | `<Time>` per plate read (RFC-2822), zeroed on first read | 23 s/cycle |
| `.tlpd` | `TempData` 1-second instrument telemetry | 23 s/cycle |
| BioRad folder | `PCREventLogXMLFile.xml` read timestamps | ~23 s/cycle |
| `.eds` (modern) | `run/quant/*.quant` → `[conditions]` `Time` (epoch s), amp stage only, zeroed on first read | run-duration spread |
| `.eds` (legacy) | `apldbio/sds/quant/*.quant` → `[conditions]` `Time` | run-duration spread |

**Regression that motivated this rule (2026-07-07):** the modern `.eds` path scanned only the *legacy* `apldbio/sds/quant/` folder, found nothing, and fell back to spreading the whole 44-minute run (initial hold + melt ramp included) across 90 cycles → 29.4 s/cycle instead of the real 21.7 s/cycle, inflating the x-axis by ~1.36× and rescaling every `t_LoD` / `10%` readout. The real per-cycle timestamps were in the file all along.

## Curve-colour invariants (read before touching any colour map)

Every surface that colours curves — the plot, the plate grid, the Kinetics Report — must resolve colour **identically**, or they visibly disagree. Three rules, each learned from a real bug:

1. **Build the colour map over the SAME well set the plot draws** (populated, **not hidden**, **not deactivated**). `buildColorMap` divides the palette among *units* (a group = one unit; an ungrouped well = one unit), so including extra wells **resplits the whole palette** and shifts every colour. Symptom: grid/report colours are "close but not the same" as the curves. (Bit us twice: `WellGrid` coloured over all used wells, and `KineticsReport` over all non-deactivated wells, while the plot used the visible set.)
2. **Use the shared [`buildColorMap`](src/lib/curve-colors.ts) — never reimplement it.** `WellGrid` carried an inline duplicate that silently drifted. Precedence is always: per-curve override → per-well override → grouped/Tt-ordered palette (`resolveCurveColorWidth` layers the overrides on top of the base map).
3. **Resolve the *effective* group: `curveGroups[curveKey(well, channel)] ?? wellGroups[well]`.** Since the curve-centric migration (#45) all grouping actions write `curveGroups`; anything still reading only the legacy `wellGroups` sees an empty map and silently falls back to per-well colours, so grouped wells never share a colour.

Also: `buildColorMap`'s Tt sort must stay **stable** (`(a - b) || 0`). With threshold detection off (the default) every Tt is `null → Infinity`, and `Infinity − Infinity = NaN` is an inconsistent comparator that V8 sorts unpredictably — letting two surfaces order the same groups differently and assign different palette colours.

### Palette application model: select stages, Apply commits, the result sticks

The palette dropdown is **non-destructive** — it only stages a choice. **Apply** (`applySelectedPalette` → `applyPaletteToChannel`) assigns the palette, by Tt order, to the curves that are **shown at that moment** (visible = not hidden, not deactivated) and **persists it as per-curve `curveStyleOverrides`**. Because the assignment is *stored* rather than re-derived, it **sticks**: hiding or showing wells afterwards never recolours them. Pressing Apply again re-spreads over the new hide state.

Consequences to keep in mind:
- **`Reversed` and `Group colors` are Apply *options*, not live toggles** once a palette has been applied — overrides outrank the live `buildColorMap`, so they take effect on the next Apply. The hint text says so.
- The **live `buildColorMap` is only the default** for curves with no override. Its domain is the experiment's **active wells** (all but deactivated), *not* the visible subset — so un-applied curves don't shift when a well is hidden/shown either.
- **"Clear custom colors"** wipes `curveStyleOverrides`, which also discards an applied palette and reverts to the live default. That's the intended reset.
- `applyPaletteToChannel` must exclude **both** hidden and **deactivated** wells (it once excluded only hidden, and would have spread the palette across all 75 empty wells of a QS `.eds`).

## Instrument File Formats & Encryption

Most instrument formats are parsed in pure TypeScript (`src/lib/parsers/`). The Python sidecar (`scripts/parse_instrument.py`) is used as a fallback for formats requiring v1 parser dependencies. Key details for each format:

### BioRad CFX96 (.pcrd)
- **Structure:** Nested ZIP → inner `datafile.pcrd` entry is ZipCrypto encrypted → UTF-8 XML
- **Password:** `SecureCompressDecompressKeyiQ5V4Files!!##$$`
- **Source:** Hardcoded in Bio-Rad CFX Manager's `BioRad.Common.dll` (`FileCryptor` class)
- **XML root:** `<experimentalData2>` — contains plate setup, protocol, fluorescence data (PAr blobs), per-cycle timestamps, RunInfo (66 KV pairs), event log
- **PAr data:** 2592 semicolon-separated floats per plate read: 108 wells × 4 stats × 6 channels. Index: `c*432 + w*4 + stat`. Wells 0-95 = data (A1-H12), 96-107 = reference (skip)
- **Channels / fluorophores (multichannel):** all 6 optical channels are extracted (`extractAllChannels` in `pcrd.ts`). Channel→dye assignment is read from `<plateSetup2><dyeLayersList><dyeLayer><fluor channelPosition="N" fluorName="FAM" .../>` — `channelPosition` is the PAr channel index, `fluorName` the dye. Assigned dye layers are authoritative; a channel is emitted only if it carries real signal (unused channels are exactly 0 throughout the blob). With no dye layers, channels with data are named `Channel N`. Canonical channel ID = dye name. A single-dye run (e.g. SHARP/SYBR) loads as one channel and hides the channel UI.
- **Plate layout:** Always 96-well (8×12), defined by `plateSetup2` XML section
- **Full reverse engineering notes:** `PCRD_FORMAT.md` in v1 repo

### TianLong Gentier (.tlpd)
- **Structure:** Password-protected ZIP archive
- **Password:** `82218051`
- **Contents:** INI-style text files (`experiment_data`, `run_method`, `coefficient`, `experiment_log`)
- **AmpData:** Hex-encoded uint16 LE fluorescence values, N wells per cycle (N = well count from model)
- **MeltData:** Same hex format, temperatures derived from protocol step definitions
- **Channels / fluorophores (multichannel):** each AmpData/MeltData cycle blob holds a fixed **6 optical-channel slots**; well `w` of channel-slot `c` is at uint16 index `c*stride + w` where `stride = floor(uint16Count / 6)` (≈97 = 96 well slots + 1 trailer). Channels used carry data in the first slots; the rest are all-zero. The channel→dye map is `run_method`'s `[DyeInfo]` section: `Dye\N\Name` (FAM/HEX/…), `Dye\N\Enable`, `Dye\size`; the i-th enabled dye occupies channel slot `i-1` (DyeInfo order = slot order). Single-dye files (`Dye\size ≤ 1`) load through the unchanged single-channel path. Verified on `a private multichannel fixture` (Sample data) → 2 channels FAM+HEX with isolated per-channel amp+melt.
- **Step definitions:** 26-byte hex blobs — temp at offset +2 (uint16 LE, hundredths °C), hold time at +10, read flag at +14
- **SampleSetup Well blobs:** `Well\N\Value` in `[SampleSetup]` section — hex-encoded binary per well:
  - Byte 0: active flag (01 = populated, 00 = empty)
  - Bytes 4-7: color (RGBA)
  - Bytes 12+: sample name (ASCII, null-terminated)
  - `Well\N\Value\Test`: same structure, contains Test Name field (preferred over Sample name)
- **Well count:** Determined from `InstrumentTypeName` in `FileInfo` section via model lookup
- **Physical layout:** Mapped from instrument model (not stored in file): Gentier Mini → 2×8, Gentier 48 → 6×8, Gentier 96 → 8×12
- **Well name mapping:** 0-based index → row/col: `index / cols` → row letter, `index % cols + 1` → column number
- **Time reconstruction:** `TempData` section contains real 1-second resolution instrument telemetry

### ThermoFisher QuantStudio (.eds)
- **Structure:** ZIP archive (unencrypted). Modern layout (`summary.json` present): `setup/plate_setup.json`, `setup/run_method.json`, `primary/analysis_result.json`, `primary/multicomponent_data.json`, `run/run_summary.json`, `run/quant/*.quant`.
- **Two formats:** Modern (JSON-based, `summary.json` present) and legacy (`apldbio/sds/experiment.xml` + `.quant`).
- **Invalid-JSON guard (important):** QuantStudio writes **bare `NaN` / `Infinity`** in `analysis_result.json` (undetermined values, e.g. `cq` on a NO_AMP well). That is not valid JSON — JS `JSON.parse` rejects it (Python's `json` is lenient, which masks it during inspection). `readJson` (`eds.ts`) strips `NaN`/`Infinity` in value position (never inside a quoted string) and retries. Without this the whole modern path silently returns nothing.
- **Amplification signal = raw reporter dye, NOT `rn`.** `analysis_result.json`'s `rn` is `SYBR/ROX` (ROX-normalized). SHARP's chemistry has no ROX (no passive reference in the mix), so `rn` is division-by-noise. The parser plots the **raw dye fluorescence** from `primary/multicomponent_data.json` (`wellData[].dyeData[].fluorescences`, sliced to the amplification stage via `collectionPoints[].stage` = the run-method PCR stage) — matching how `.pcrd`/`.tlpd`/legacy `.eds` feed raw fluorescence. Falls back to `rn` only if multicomponent is absent.
- **Melt:** per-reaction `meltResult` (`rn` + `rnTemperatures`, 109 pts here). Shared temperature axis = first well's `rnTemperatures`; derivative **recomputed** via `computeMeltDerivative` (the file's `derivativeRn` sits on a different axis). `has_melt` keys off parsed melt.
- **Timing (real timestamps — see "Parser Principles"):** per-read acquisition times live in `run/quant/*.quant` → `[conditions]` → `Time` (Unix epoch seconds). The filename encodes `S{stage}_C{cycle}_T…_P…_M{e}_X{x}_E{n}.quant`, so take **one read per amplification-stage cycle** and rebase on the **first amp read** (cycle 1 → t 0, matching `.pcrd`). Two traps: (1) modern files put quant under `run/quant/`, NOT the legacy `apldbio/sds/quant/`; (2) the modern `[conditions]` block is a tab-separated **header row + value row**, so the legacy `Time<TAB>value` reader (`parseQuantTime`) never matches — use `parseQuantConditionTime`. Getting this wrong silently falls back to spreading the whole run (init hold + melt ramp) across the cycles: 29.4 s/cycle instead of the real 21.7 s/cycle.
- **Protocol (`run_method.json`):** qPCR File API 2.0 schema — stages carry `repeat` (not `cycleCount`); steps nest temp/duration under `ramp`/`hold`; a collecting step has a `collectionProfile` (`PCR_HAC_SETTING` = amplification read, `MELT_RAC_SETTING` / `collectionMode:"CONTINUOUS"` = melt ramp). `parseRunMethodJson` handles this and keeps the older string-named schema (`name`/`cycleCount`/`collectData` + "PCR"/"MELT" names) as a fallback.
- **Channels / fluorophores:** channel labeled by **dye** (reporter), not target. `targetName→reporter` map from `plate_setup.targets` (`{name:"16s", reporter:"SYBR"}`); a dye field on the reaction wins if present, else the target's reporter, else the target name.
- **Well labels:** `sample = sampleName || wellName` — a well with no operator-entered sample name falls back to its position (never blank), matching `.pcrd`.
- **Empty-well detection:** QuantStudio assigns a target to the **whole** plate, so every well looks populated even when only some were loaded (no emptiness flag in the file). A loaded well fluoresces from its intercalating dye; an empty one sits at background. `eds.ts` flags empties by a **top-anchored gap** on the raw-dye pre-amplification baseline (find the tight loaded cluster, cut below it; robust to a low outlier and to a well stranded in the gap; conservative — keeps ambiguous wells; also honours any plate-setup-unconfigured well). Returned as `ExperimentData.autoEmptyWells` (transient); `loadExperiment` seeds them into `deactivatedWells`.
- **`deactivatedWells` (a true "off" state):** previously an inert store field (setters, no reader). Now wired as the real deactivate/exclude concept — excluded from `visibleWells`, the WellGrid populated set, analysis pooling (drift/run-σ), results, well list, and bulk-select. Reversible + session-persisted (rides `.sharpx`). Empty-well auto-detection seeds it; the future **Configure Plate** UI will edit it. (`.pcrd`/`.tlpd` pre-filter empties at parse, so their `deactivatedWells` stays empty and every filter is a no-op.)
- **Plate layout:** 96-well (8×12).

### Agilent AriaMx (.amxd / .adxd)
- **Structure:** Double-encrypted: outer PGP TAR (.amxd) → inner PGP TAR (.SPM) → XML files
- **GPG key:** ID `3F1AF07D202BF668`, empty passphrase. Must be imported: `gpg --import ariamx_key.asc`
- **Fluorescence:** Hex-encoded 1160-byte binary packets in `InstrumentData.xml`. Header 8 bytes; 6 channels × 96 wells × 2 bytes (uint16 LE). Channel order: CY5(0), ROX(1), HEX(2), FAM(3), SYBR(4), CY3(5)
- **Primary channel:** Auto-detected from first packet (non-ROX channel with most non-zero wells)
- **Plate layout:** 96-well (8×12)
- **Requires:** GPG on PATH with AriaMx key imported

### Instrument Plate Layouts

Physical plate dimensions are NOT stored in most instrument files. The app uses this priority chain:
1. Explicit `plate_layout` in `.sharp` metadata (if present)
2. Instrument model lookup (`constants.ts:INSTRUMENT_PLATE_LAYOUTS`)
3. Inferred from well names in data (max row letter + max column number)
4. Default: 8×12 (standard 96-well)

## .sharp File Format (Quick Reference)

ZIP archive (rename to `.zip` to open) containing:

| File | Required | Description |
|------|----------|-------------|
| `metadata.json` | Yes | Authoritative machine-readable metadata. Format version, instrument, protocol, run info, per-well sample + analysis outputs, data summary, plate layout, time reconstruction. |
| `amplification.csv` | Yes | Wide format: `cycle, time_s, time_min, A1, B1, ...` (RFU) |
| `melt_rfu.csv` | No | Wide format: `temperature_C, A1, B1, ...` |
| `melt_derivative.csv` | No | Wide format: `temperature_C, A1, B1, ...` (-dF/dT) |
| `wells.csv` | 1.1+ | Flat well manifest — `well, sample, content, cq, end_rfu, melt_temp_c, melt_peak_height`. Spreadsheet-friendly view of what's also in `metadata.json > wells`. CSV-quoted for commas/quotes in sample names. Preferred for user-editable fields on read; `metadata.json` still authoritative for structure. |
| `SUMMARY.txt` | 1.1+ | Plain-text human overview of the experiment. Regenerated on every write. Not read by the app. |
| `parsing_log.json` | No | Append-only parse history |
| `session.json` | `.sharpx` only | Working-session view state — selections, hidden wells, baseline / normalization / drift settings, threshold, style, x-axis, plot tab, groups, per-well overrides, dilution config. Sets serialized as arrays, Maps as `[key, value]` arrays. Written only by **Save Session** (`.sharpx`), never by plain **Save as .sharp**. Restored by `loadExperiment` on open. |

**`.sharp` vs `.sharpx`:** identical ZIP layout; a `.sharpx` additionally contains `session.json`. `.sharp` = shareable data only; `.sharpx` = data + your working session, for resuming later. Either extension opens through the same loader.

**metadata.json key sections:** `format_version` (currently "1.1"), `instrument` (manufacturer, model, serial), `run_info` (operator, notes, timestamps), `protocol` (type, temp, cycles, melt config), `wells` (per-well: sample, content, Cq, melt peaks), `data_summary` (wells_used, cycle count), `plate_layout` (rows, cols — added by v2), `time_reconstruction` (source, cycle duration stats). Full spec at [docs/SHARP_FORMAT.md](docs/SHARP_FORMAT.md).

**Well name format:** `{row_letter}{column_number}`, no zero-padding. E.g., `A1`, `B3`, `H12`. Sorted row-first.

**Experiment types:** `sharp` (isothermal 65°C), `unwinding` (~37°C), `standard_pcr` (thermal cycling), `fast_pcr`, `isothermal`, `unknown`

**Full spec:** `SHARP_FORMAT.md` in v1 repo

## Known Issues / Workarounds

- **react-plotly.js CJS interop:** `react-plotly.js` and its factory are CJS. With Vite + `esModuleInterop`, we use `plotly.js-dist-min` + `createPlotlyComponent` factory with a runtime `.default` fallback to handle the namespace object. See `PlotArea.tsx`.
- **Plotly.js bundle size:** ~3.5 MB (using `plotly.js-dist-min`). Fine for dev, consider custom partial bundle later.
- **verbatimModuleSyntax:** Disabled in `tsconfig.app.json` because it breaks CJS default imports. Using `esModuleInterop` + `allowSyntheticDefaultImports` instead.
- **Shell scoping for Python sidecar:** `Command.create('python-parser', ...)` uses a scoped command defined in `src-tauri/capabilities/default.json`. The command name must match the scope — don't use raw executable paths with `Command.create()`.
- **Hover-highlight scrapped:** Intentionally removed — user determined it was not useful. State fields remain in Zustand store but are unused.
